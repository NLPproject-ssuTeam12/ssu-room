# SSU:room

학과사무실 조교의 강의 시간표 편성·조율 도우미

숭실대학교 자연언어처리 텀 프로젝트 · 12조 (강민우, 김대원, 문하윤, 최재성)

## 왜 만드나

학과사무실 조교 1명이 강의 약 100개의 시간과 강의실을 약 두 달 동안 엑셀과 전화·메일로 편성합니다. 시간이 겹치면 교수님과 한 건에 최대 10번까지 연락이 오가고, 답은 최대 1주가 걸립니다. 자동 편성 연구는 배정까지만 다루고, 교수와 주고받는 조율은 여전히 사람이 직접 합니다.

SSU:room은 **AI가 교수 글을 읽고, 솔버가 시간표를 짜면, 조교가 확정**하는 구조로 이 과정을 한 곳에 모읍니다.

근거: 2026-10-23 교무처 학사팀·AI소프트웨어학부 학과사무실 조교 인터뷰, 10/28 조교 메일

## 핵심 기능

1. **규칙을 지키는 자동 초안**: 건물·교양필수·채플·겹침·실습실 규칙을 지키며 초안을 짜고, 밀린 강의에는 대안 A·B·C를 제시합니다.
2. **회신을 읽는 차수별 AI 조율**: 밀린 교수에게만 조율 메시지(겹친 사실, 요청 원문, 대안 A·B·C)를 보내고, 답장을 AI가 해석해 처리안을 만듭니다. 조교가 [확인]·[수정]·[현재대로 유지] 중 하나를 눌러야 반영되고, 수정하면 사유가 남습니다. 회신 기한은 1주이고 기한 전에 자동으로 다시 알립니다. 차수당 1주, 최대 3차 뒤에는 조교가 정합니다.

## 처리 흐름

```
① 첫 초안   교수 희망 → 희망 해석(AI) → 초안 배정(솔버) → 초안 확인(조교) → 초안 공개
② 조율      교수 답장 → 회신 해석(AI) → 처리안 확인(조교) → 재배정(솔버) → 차수안 공개
            남은 겹침이 있으면 ②를 반복, 최대 3차 후 조교 결정
③ 확정      엑셀로 내보내기 → 조교가 SAP에 입력
```

- 첫 초안은 솔버가 먼저 짜고 조교가 확인합니다. '확인 필요'로 표시된 애매한 해석도 이때 봅니다.
- 재배정은 확인된 조건만 반영하고 이전 배정을 최대한 유지합니다.
- 모든 단계는 SQLite에 분반, 가능 시간, 배정 이력, 규칙 예외 사유를 기록합니다.

> 위 "핵심 기능"·"처리 흐름"·"NLP가 하는 일"은 중간 발표(11/5) 기준입니다. 그 뒤 회의에서 바뀐 것은 바로 아래 절에 정리했고, 둘이 다르면 아래를 따릅니다.

| 점수가 같아 두 분반이 같은 희망 칸을 두고 맞서면 ① 가능한 시간이 적은 분반 ② 먼저 임용된 교수 ③ 과목·분반 번호 순서로 정한다 (같은 입력이면 같은 결과) | 11/25 | `user.hire_year` (011), 엔진 동점 순서 |
| 연강 동선: 같은 학년 전공 과목이 같은 요일 이어진 교시에 같은 건물이면 좋은 배치로 본다(강의실은 달라도 됨, 다른 학년은 없음). 교수 희망·건물이 항상 먼저 | 11/25 | 엔진 두 단계 풀이(1단계 원래 점수, 2단계 동선만) |
| 기타만 고르고 조율할 내용이 없으면 프로그램에서 더 조율하지 않고 조교가 다른 연락망으로 교수와 정한다. 조교가 정한 시간은 수동 배치하고 바꾸기 어려운 것으로 보아 고정한다 | 11/25 | 안건 상태 `OFFLINE`, `db.manual_place`(규칙 위반은 막지 않고 `check_timetable`로 경고), `timetable_section.locked`로 이후 모든 풀이에서 고정 |

실제 데이터로 잰 결과: AI소프트웨어학부 2026-2학기 전공 개설 강좌(분반 82개)에서 응답 없음은 약 10–14초, 실제 시간을 희망으로 둔 경우는 약 8–11초에 최적해를 찾았고 못 놓은 분반은 0개였습니다. 강의실 정원·불가 칸·채플 시간은 가정이고, 실제 시간표가 이미 하나의 답이라 0개는 당연한 결과입니다(자세한 것은 `solver/README.md` "실제 데이터 측정").

## NLP가 하는 일

| 역할 | 예 |
|---|---|
| 희망 해석 | "화·목 오후, 실습실 필요" → 가능 시간과 실습실 조건 |
| 회신 분류 | "A나 C 다 괜찮아요. 수요일은 17시 전에 끝나야 해요" → 조건부 수용(A·C), 수요일 17시 전 종료 |
| 중립 조율 메시지 | 연차나 상대 교수 이름 없이 겹침과 대안만 전달 |

언어 모델은 배정을 정하지 않습니다. 모든 출력은 Pydantic으로 형식을 검증하고, 키워드 규칙 기준선과 같은 정답으로 비교합니다.

## 배정 방식 비교 실험

중간 발표(11/5) 때 배정 엔진으로 CP-SAT를 고른 근거입니다. 그때 엔진으로 합성 데이터 100분반, 강의실 18개, 시드 10개를 비교했습니다. 그때 실험 코드는 이 저장소에 없고, 지금 엔진으로 다시 잰 결과와 코드는 바로 아래 절(`experiments/`)에 있습니다.

| 지표 | 그리디 + 규칙 기반 | CP-SAT 시간 + 강의실 동시 배정 |
|---|---|---|
| 하드 제약 위반 | 0건 | 0건 |
| 연강 먼 이동 | 7.5회 | 0회 (10개 시드 모두) |
| 종합 효용 | 기준 | +9.7% (10개 시드 모두 우세) |
| 연구실 건물 배정률 | 98.0% | 94.1% |
| 실행 시간 | 즉시 | 25초 |

- 비교군은 수작업을 흉내 낸 시간 그리디와 강의실 그리디입니다.
- 이동 항을 목표에서 빼면 CP-SAT의 먼 이동이 11.2회로 오히려 늘어납니다.
- 합성 데이터 실험이며 실제 편성 결과가 아닙니다.

## 회신 해석 평가

교수 답장을 판정(수용·조건부·거절·확인 필요), 고른 안, 조건(요일·교시·종료 시각)으로 바꾸는 기능의 평가입니다. 키워드 규칙을 비교 기준으로 둡니다.

- **상황:** AI소프트웨어학부 2026-1·2학기 실제 개설 강좌 시간표로 만든 조율 상황 20개. 과목·분반·강의실·시간은 실제 값, 교수 이름은 가명, 겹침과 대안은 꾸민 상황입니다
- **답장:** 팀원 4명이 교수 역할로 직접 쓴 80개. 언어 모델로 만들지 않았습니다
- **정답:** 최재성 한 명이 달았습니다. 16개는 프롬프트를 고칠 때 보는 dev, 64개는 test입니다
- **새 세트:** 규칙·프롬프트를 다 고친 뒤 새 상황 5개(s21~s25)로 받은 답장 20개. 아무도 미리 보지 않은 마지막 평가입니다

결과 (언어 모델 = gemini-3.5-flash-lite)

| 세트 | 방식 | 판정 정확도 | 받아들임 여부 | 고른 안 일치 | 조건 F1 | 처리안 일치 | 위험 오류 |

- 위험 오류 = 정답이 거절·확인 필요인데 수용·조건부로 읽은 수. 키워드 규칙은 "C가 괜찮을 것 같긴 한데… 다음 주에 다시 말씀드려도 될까요"를 C 수용으로 읽는 식의 오류가 있었고, 언어 모델은 두 세트 모두 0건입니다

- 11/26 새 세트에서 조건 F1이 0.82 → 0.755로 내려간 것은 같은 답장을 실행마다 다르게 읽은 문장 두 개(j24 "월수 1시반은 비어 있나요?"를 조건으로 좁혀 읽음, j21) 때문입니다. 조건 일치(문장 단위)는 0.833 (키워드 0.400). 키워드 줄은 11/22 뒤 규칙(요일별 교시)이 바뀌어 지금 코드로 다시 쟀습니다
- 11/25 다시 잼: 답장 화면이 버튼 여러 개·순서·'지금 자리 그대로'로 바뀌어(#19) 프롬프트가 달라졌기 때문입니다. 한 번 잰 값이 실행마다 크게 달라서 같은 코드로 4번 재고 4번 모두 적었습니다 (좋은 회차만 고르지 않음)
- 회차마다 숫자가 흔들린 주된 이유는 Gemini 무료 서버 과부하(503)입니다. 세 번 다시 시도해도 막히면 키워드 방식으로 넘어가는데, 넘어간 답장이 회차마다 3·1·0·17개였습니다. 모델이 실제로 답한 답장만 보면 판정 0.902~0.936, 조건 일치(문장 단위) 0.918~0.957로 고릅니다
- 조건 일치(문장 단위) = 조건을 통째로 맞힌 답장 비율. 4번 평균 0.903 (0.844~0.938). 조건 F1은 요일×교시 칸 단위라 요일 하나만 틀려도 크게 내려가서, 11/25 결과를 본 뒤 보조 지표로 더했습니다
- 시연은 리허설 때 저장해 둔 응답을 쓰므로 과부하 영향을 받지 않습니다. 실제로 쓸 때 과부하가 길면 해석이 '확인 필요'로 내려가 조교가 직접 봅니다
- 처리 시간은 답장 하나에 평균 4~5초입니다 (키워드 0초. 11/25 측정은 과부하 재시도 때문에 평균 9초 이상)
- 한계: 정답을 한 사람이 달아 일치도(카파)를 잴 수 없습니다. 답장은 팀원이 교수 역할로 쓴 것입니다
- 측정 이력, 바꾼 것, 오류 분석: [docs/planning/회신해석_평가.md](docs/planning/회신해석_평가.md) · 실행: `python eval/run_coord.py reply --method llm --split test`

## 조율 메시지 사람 평가

교수에게 보내는 조율 메시지는 정답이 하나가 아니라 사람이 채점했습니다 (상황 25개, 언어 모델 글 25개 + 틀 문장 25개를 섞어 방식을 가리고 채점, 채점자 1명).

| | 틀 문장 (기준선) | 언어 모델 1차 | 언어 모델 2차 |
|---|---|---|---|
| 내용 맞음 | 1.00 | 0.96 | 0.96 |
| 지어낸 말 없음 | 1.00 | 0.88 | 1.00 |
| 금지 내용 없음 | 1.00 | 1.00 | 1.00 |
| 자연스러움 (1~5) | 5.00 | 3.92 | 4.72 |

- 1차에서 언어 모델이 입력에 없는 이유("다른 과목이 배정되어")를 지어내고, 제목 줄을 문장으로 끝내지 않았습니다. 코드 검사는 이것을 잡지 못했습니다
- 그래서 인사·제목·대안·마지막 문장은 틀로 고정하고, 언어 모델은 상황 설명 문단만 쓰게 바꿨습니다. 설명 문단은 코드가 다시 검사합니다 (대안 설명, 없는 시각, 지어낸 이유, 상대 이름 빠짐)
- 2차에서도 틀 문장이 모든 칸에서 같거나 나았습니다
- 채점 기준·결과: [docs/planning/메시지_사람평가.md](docs/planning/메시지_사람평가.md) · 실행: `python eval/run_coord.py message --method llm`

## AI 도우미 평가

조교 질문 20개(김대원 작성, 최재성 라벨)로 의도와 정보(과목·분반·교수·요일·시각·강의실·건물)를 맞게 뽑는지, 정보가 모자랄 때 되묻는지를 잽니다.
키워드 규칙(기준선)과 언어 모델(Gemini Flash Lite)을 같은 정답으로 비교합니다. 결과 파일: `eval/results/assistant_*`.

| | 키워드 11/24 (개선 전) | 언어 모델 11/25 (개선 전) | 키워드 11/25 (개선 후) | 언어 모델 11/26 (개선 후) |
|---|---|---|---|---|
| 의도 정확도 | 0.85 | 0.95 | 1.00 | 1.00 |
| 정보 F1 | 0.915 | 0.949 / 0.931 | 0.951 | **0.984** |
| 되묻기 정확도 | 0.65 | 0.75 | 0.90 | 0.90 |
| 키워드로 대신 처리 | — | 20개 중 4개 (두 번 잼) | — | 0개 |

- **지표:** 의도 정확도 = 맞힌 의도 비율. 정보 F1 = 뽑은 정보 항목의 정밀도·재현율 조화평균. 되묻기 정확도 = 물어야 할 때 묻고, 안 물어야 할 때 안 묻는 비율
- **키워드로 대신 처리:** 무료 티어 언어 모델이 막히면(429·503) 키워드 결과로 답한다. 그 수를 따로 적는다. 개선 전 언어 모델 칸은 그 4개가 섞인 값이다
- **개선 내용(11/25):** 과목 줄임말 표를 한 곳(`backend/app/nlp/aliases.py`)에 모으고 두 방식이 같이 쓰게 함, 같은 이름 과목은 과목 코드·학과·학년으로 되묻기, 키워드에 "A 말고 B", 옮기기 동사(당겨·미뤄·빼 줘), 가정 표현(겹쳐·문제 없어·자리 있어), 현황(답장·회신·몇 차), 시간표 밖 일(수강신청·메일 등) 우선
- **한계:** 문장이 20개뿐이라 한두 문장에 수치가 크게 움직인다. 라벨러가 1명이라 두 사람 일치도가 없다. 평가 문장은 AI가 쓴 초안을 팀이 합의해 썼다. 개선은 일반 규칙으로만 했고 평가 문장에 맞춰 특정 문장을 고치지 않았지만, 같은 20문장으로 다시 잰 값이라 새 문장에서는 더 낮을 수 있다.
- 개선 후 언어 모델은 정보 F1에서 키워드보다 높고(0.984 vs 0.951), 되묻기는 둘 다 8개 중 6개만 물었다
- 실행: `python eval/run_assistant.py --method keyword` / `--method llm --sleep 4` (질문 사이 4초 쉼, 429·503이면 한 번 더 기다렸다 다시)

    nlp/          조율 NLP(coord.py: 조율 메시지·회신 해석·처리안), AI 도우미(assistant.py), 언어 모델 호출(llm.py), 프롬프트
  tests/          서버·조율·도우미 테스트
  tools/          DB 시드, 실제 데이터 가져오기 (교수 이름은 가명으로)

  synthetic/      가상 데이터 (커밋)
  private/        실제 자료 원본 (커밋 금지)
eval/             평가 스크립트
  labels/         평가 답장과 정답 (사람이 작성)
  results/        측정 결과
experiments/      배정 방식 비교 실험 (그리디 기준선 vs 배정 엔진)
docs/
  midterm/        중간 발표 덱과 대본
  prototype/      화면 시안
  planning/       라벨링 가이드, API 명세, 평가 문서
  meetings/       회의록

## 개발 환경 준비

Python 3.11 이상을 기준으로 합니다.

```bash
git clone https://github.com/NLPproject-ssuTeam12/ssu-room.git
cd ssu-room

python -m venv .venv
# Windows: .venv\Scripts\activate
# macOS·Linux: source .venv/bin/activate

cp .env.example .env   # Windows: copy .env.example .env
```

`.env`에는 각자 발급받은 API 키를 넣습니다. `.env`는 절대 커밋하지 않습니다.

테스트: 저장소 맨 위에서 `python -m pytest backend/tests -q` (backend/ 안에서는 `python -m pytest tests -q`).

## 실행 방법

1. **설치:** 위 "개발 환경 준비"처럼 `.venv`를 만들고 `pip install -r backend/requirements.txt`
2. **언어 모델 키:** `.env`에 `GEMINI_API_KEY=…`. 없으면 조율 메시지·회신 해석·AI 도우미가 모두 키워드 방식으로 돈다
   - **기본 해석 방식:** `SSUROOM_NLP=llm`이면 화면이 `method`를 안 보내도 언어 모델로 돈다(없으면 `keyword`). Windows `set SSUROOM_NLP=llm` / macOS·Linux `export SSUROOM_NLP=llm` (또는 `.env`에 한 줄). 요청에 `method`를 주면 그게 우선이고, 언어 모델이 막히면(429·503·키 없음) 키워드로 대신 처리한다
3. **데이터 넣기(시드):** 강의정보 엑셀 → DB(`ssuroom.db`)와 분반 대응표. 시연은 `--demo`
   ```bash
   python backend/tools/seed_db.py          # 실제 강의 목록 + 교수 가명 + 가상 희망(실제 강의 칸)
   python backend/tools/seed_db.py --demo --blank-prof   # 시연용: 가상 희망 일부를 겹치게(조율 대상이 생김) + 교수 한 명의 희망을 비워 둠
   ```
4. **서버 켜기 (DB 모드):** 배정은 하윤 엔진, 상태는 DB에 저장
   ```bash
   SSUROOM_ENGINE=solver uvicorn backend.app.main:app --port 8000        # macOS·Linux
   $env:SSUROOM_ENGINE="solver"; uvicorn backend.app.main:app --port 8000  # Windows PowerShell
   ```
   `SSUROOM_ENGINE` 없이 켜면 **메모리 모드**다: 배정 엔진이 가짜 함수(stubs.py)라 테스트·화면 연결용이고, 시연에는 쓰지 않는다
5. **화면:** React 화면(`frontend/`, 강민우)은 따로 켠다 (Vite 기본 http://localhost:5173). 서버는 이 주소만 CORS 허용
6. **테스트:** `python -m pytest backend/tests -q` (키 없이 돈다. 실제 언어 모델 테스트 2개는 건너뜀)

API는 [docs/planning/API명세.md](docs/planning/API명세.md)를 본다.

## 시연 준비

- **노트북 2대:** 조교 화면(서버를 켠 노트북)과 교수 화면(같은 서버 주소로 접속). 교수 답장은 시스템 안에서만 받는다
- **준비:** `python backend/tools/seed_db.py --demo --blank-prof` → 서버를 DB 모드로 켬. 2026-2 엑셀 기준 초안이 약 25~30초, 조율 대상 OPEN 5·HOLD 2·NO_OPTION 1 (11/27 측정). 시드 끝에 "희망 비운 교수: 교수NN (분반 …)"이 나온다
- **희망 수집부터:** 희망 비운 교수로 시연을 시작 → 교수 화면에서 희망 칸·인원·분반 연강을 입력 → 조교 화면에서 희망 확인 → 초안
- **언어 모델 켜기:** `.env`에 `GEMINI_API_KEY=…`, 서버 켜기 전에 Windows `set SSUROOM_NLP=llm` / macOS·Linux `export SSUROOM_NLP=llm`. `GET /health`의 `nlp`가 `llm`, `gemini_key`가 `true`인지 확인
- **순서:**
  1. 초안 만들기 → 시간표와 조율 대상(못 놓음·어긋남·일부 어긋남·대안 없음) 확인
  2. 1차 조율 시작 → 조율 메시지 자동 발송 (일부 어긋남은 조교가 [보내기], 대안 없음은 [확인] → 따로 연락)
  3. 교수 화면에서 답장 (A·B·C·기타·지금 자리 그대로)
  4. 조교 화면에서 회신 해석·처리안 확인 → [확인]·[수정]·[현재대로 유지]·[따로 연락]
  5. 2차 조율 (확인한 조건을 쌓은 새 대안) → 확정 → 엑셀 내보내기
  6. AI 도우미 질문: 이유 설명("…은 왜 밀렸어?"), 가정 실행("정보과학관 21303 공사하면?"), 이동("…를 월수 12시로 옮겨줘" → [적용])
- 무료 티어 언어 모델이 막힐 때를 대비해 시연 응답을 미리 저장해 둔다(`LLM_CACHE_DIR`)

### 컴퓨터 2대 시연

컴퓨터 A(조교)가 서버와 화면을 켜고, 컴퓨터 B(교수)는 브라우저로 A에 들어와 같은 서버·DB를 씁니다. 아래는 Windows 기준입니다.

1. **같은 네트워크:** 두 대 모두 핸드폰 핫스팟에 연결한다 (학교 와이파이는 기기끼리 접속을 막을 수 있음)
2. **컴퓨터 A 서버:** `ipconfig`로 IPv4 주소(A의IP)를 확인하고
   ```bat
   set SSUROOM_ENGINE=solver
   set SSUROOM_NLP=llm
   set SSUROOM_LAN=1
   uvicorn backend.app.main:app --host 0.0.0.0 --port 8000
   ```
   macOS는 `set` 대신 `export SSUROOM_ENGINE=solver SSUROOM_NLP=llm SSUROOM_LAN=1`, IP는 `ipconfig getifaddr en0`
3. **컴퓨터 A 화면:** `frontend`에서 `npm run dev -- --host`. 화면이 접속한 주소를 따라가는 버전이면 다른 설정은 필요 없고, 안 따라가는 버전이면 먼저 `set VITE_API_BASE=http://A의IP:8000`
4. **컴퓨터 B:** 브라우저로 `http://A의IP:5173` → 교수로 들어간다
5. **방화벽:** 처음 켤 때 Windows 방화벽 창이 뜨면 "개인 네트워크"를 허용한다
6. **확인:** B 브라우저에서 `http://A의IP:8000/health`가 열리고 `lan`이 `true`
- 화면이 몇 초마다 다시 불러오지 않는 버전이면, 상대가 바꾼 내용은 새로고침(F5)해야 보인다
- `SSUROOM_LAN`은 사설망(192.168.x.x·10.x.x.x·172.16~31.x.x)의 5173 포트만 허용한다. 사설망 주소가 아니면 `set SSUROOM_CORS=http://주소:5173`(쉼표로 여러 개)

## 저장소 사용 규칙

### 1. 기본 흐름

```
main 최신화 → 브랜치 만들기 → 작업·커밋 → push → PR → 리뷰 1명 승인 → 병합 → 브랜치 삭제
```

```bash
git switch main
git pull
git switch -c feat/solver-hard-rules
# 작업
git add 바꾼파일
git commit -m "solver: 교양필수 시간 규칙 추가"
git push -u origin feat/solver-hard-rules
# GitHub에서 PR 만들기
```

- **main에 직접 push하지 않습니다.** 모든 변경은 PR로 들어갑니다. 무료 비공개 저장소라 설정으로 막을 수 없으니 팀 약속으로 지킵니다.
- 작업을 시작하기 전과 PR을 올리기 전에 `git pull`로 main을 최신으로 맞춥니다.

### 2. 브랜치 이름

`종류/짧은-영어-설명` 형식으로 씁니다.

| 종류 | 언제 | 예 |
|---|---|---|
| `feat/` | 새 기능 | `feat/nlp-reply-classifier` |
| `fix/` | 버그 수정 | `fix/solver-chapel-overlap` |
| `data/` | 데이터·라벨 추가 | `data/reply-labels-v1` |
| `exp/` | 실험 | `exp/greedy-vs-cpsat` |
| `docs/` | 문서·회의록 | `docs/labeling-guide` |

한 브랜치에는 한 가지 일만 담고, 작업이 끝나 병합되면 브랜치를 지웁니다.

### 3. 커밋 메시지

`영역: 무엇을 했는지` 한 줄로 씁니다. 한국어로 씁니다.

```
solver: 교양필수 10:30~15:00 규칙 추가
nlp: 회신 분류 프롬프트 첫 버전
eval: 회신 해석 정확도 계산 스크립트
data: 희망 문장 30개와 정답 추가
docs: 11/4 회의록
```

영역: `rules`, `solver`, `nlp`, `db`, `api`, `frontend`, `eval`, `data`, `exp`, `docs`

### 4. PR과 리뷰

- PR은 작게 만듭니다. 리뷰어가 15분 안에 읽을 수 있는 크기가 좋습니다.
- PR 설명에는 네 가지를 적습니다.
  1. 무엇을 바꿨나
  2. 왜 바꿨나
  3. 어떻게 확인했나 (실행한 명령, 결과)
  4. AI 도구 사용 여부 (도구 이름과 쓴 부분)
- 팀원 1명 이상이 승인해야 병합합니다. 그 영역을 맡은 사람이 리뷰하는 것을 원칙으로 합니다.
- 병합은 PR 작성자가 하고, **Squash and merge** 또는 **Create a merge commit**을 씁니다. 작업 단계를 커밋으로 남기고 싶으면 merge commit을 씁니다.
- 다른 PR의 브랜치 위에 쌓은 PR이 있으면, 앞 PR은 squash가 아니라 merge commit으로 병합합니다. squash하면 뒤 PR이 같은 내용을 다른 커밋으로 들고 있어 충돌합니다 (11/25 #17·#20·#21).
- squash로 병합한 뒤에는 자기 브랜치를 main에 맞추고 다음 작업을 시작합니다.
- 리뷰 의견은 코드 줄에 댓글로 남기고, 고친 뒤 작성자가 답글로 알립니다.

### 5. 올리면 안 되는 것

- `.env`, API 키, 비밀번호
- 실제 수요 조사 양식, 인터뷰 원본, 교수·조교 실명이 들어간 파일
- 영상 등 10MB가 넘는 파일
- 실수로 올렸다면 바로 팀에 알립니다. API 키는 즉시 폐기하고 새로 발급합니다. 기록에서 지우는 것만으로는 안전하지 않습니다.

### 6. 할 일 관리

- 할 일은 GitHub Issues에 올리고 담당자를 지정합니다.
- PR 설명에 `Closes #번호`를 쓰면 병합할 때 이슈가 자동으로 닫힙니다.
- 진행 상황은 Discord에 바로 공유하고, 회의록은 `docs/meetings/날짜.md`로 남깁니다.

### 7. 결정하는 방법

기술 판단은 그 영역 담당자가 정하고 공유합니다. 범위와 일정은 화요일 정기 회의에서 다수결로 정합니다. 체크포인트(11/12, 11/19)에서 범위를 다시 조정합니다.

## 데이터 원칙

- 시연 데이터는 **가상 데이터**이고, 화면과 발표에도 그렇게 표시합니다.
- 평가 문장은 팀원·지인이 교수 역할로 직접 쓰고, **언어 모델로 만들지 않습니다.** 라벨은 최재성 한 명이 달고(11/21 결정), 80개 중 16개는 프롬프트 개선용, 64개는 최종 평가용으로 나눕니다.
- 정답 데이터(`eval/labels/`)는 평가 스크립트만 읽습니다. 서비스 코드는 정답을 읽지 않습니다.
- 가정·시뮬레이션·목표 수치는 실측처럼 쓰지 않습니다.
