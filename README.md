# SSU:room

학과사무실 조교의 강의 시간표 편성·조율 도우미

숭실대학교 자연언어처리 텀 프로젝트 · 12조 (강민우, 김대원, 문하윤, 최재성)

## 왜 만드나

학과사무실 조교 1명이 강의 약 100개의 시간과 강의실을 약 두 달 동안 엑셀과 전화·메일로 편성합니다. 시간이 겹치면 교수님과 한 건에 최대 10번까지 연락이 오가고, 답은 최대 1주가 걸립니다. 자동 편성 연구는 배정까지만 다루고, 교수와 주고받는 조율은 여전히 사람이 직접 합니다.

SSU:room은 **AI가 교수 글을 읽고, 솔버가 시간표를 짜면, 조교가 확정**하는 구조로 이 과정을 한 곳에 모읍니다.

근거: 2026-10-23 교무처 학사팀·AI소프트웨어학부 학과사무실 조교 인터뷰, 10/28 조교 메일

## 핵심 기능

1. **규칙을 지키는 자동 초안**: 건물·교양필수·채플·겹침·실습실 규칙을 지키며 초안을 짜고, 밀린 강의에는 대안 A·B·C를 제시합니다.
2. **회신을 읽는 차수별 AI 조율**: 밀린 교수에게만 조율 메시지(겹친 사실, 요청 원문, 대안 A·B·C)를 보내고, 답장을 AI가 해석해 처리안을 만듭니다. 조교가 [확인]·[수정]·[현재대로 유지] 중 하나를 눌러야 반영되고, 수정하면 사유가 남습니다. 회신 기한은 1주이고 기한 전에 자동으로 다시 알립니다. 차수당 1주, 최대 3차 뒤에는 조교가 정합니다.

## 처리 흐름

```
① 첫 초안   교수 희망 → 희망 해석(AI) → 초안 배정(솔버) → 초안 확인(조교) → 초안 공개
② 조율      교수 답장 → 회신 해석(AI) → 처리안 확인(조교) → 재배정(솔버) → 차수안 공개
            남은 겹침이 있으면 ②를 반복, 최대 3차 후 조교 결정
③ 확정      엑셀로 내보내기 → 조교가 SAP에 입력
```

- 첫 초안은 솔버가 먼저 짜고 조교가 확인합니다. '확인 필요'로 표시된 애매한 해석도 이때 봅니다.
- 재배정은 확인된 조건만 반영하고 이전 배정을 최대한 유지합니다.
- 모든 단계는 SQLite에 분반, 가능 시간, 배정 이력, 규칙 예외 사유를 기록합니다.

> 위 "핵심 기능"·"처리 흐름"·"NLP가 하는 일"은 중간 발표(11/5) 기준입니다. 그 뒤 회의에서 바뀐 것은 바로 아래 절에 정리했고, 둘이 다르면 아래를 따릅니다.

## NLP가 하는 일

| 역할 | 예 |
|---|---|
| 희망 해석 | "화·목 오후, 실습실 필요" → 가능 시간과 실습실 조건 |
| 회신 분류 | "A나 C 다 괜찮아요. 수요일은 17시 전에 끝나야 해요" → 조건부 수용(A·C), 수요일 17시 전 종료 |
| 중립 조율 메시지 | 연차나 상대 교수 이름 없이 겹침과 대안만 전달 |

언어 모델은 배정을 정하지 않습니다. 모든 출력은 Pydantic으로 형식을 검증하고, 키워드 규칙 기준선과 같은 정답으로 비교합니다.

## 배정 방식 비교 실험

배정 엔진으로 CP-SAT를 고른 근거입니다. 합성 데이터 100분반, 강의실 18개, 시드 10개로 비교했습니다.

| 지표 | 그리디 + 규칙 기반 | CP-SAT 시간 + 강의실 동시 배정 |
|---|---|---|
| 하드 제약 위반 | 0건 | 0건 |
| 연강 먼 이동 | 7.5회 | 0회 (10개 시드 모두) |
| 종합 효용 | 기준 | +9.7% (10개 시드 모두 우세) |
| 연구실 건물 배정률 | 98.0% | 94.1% |
| 실행 시간 | 즉시 | 25초 |

- 비교군은 수작업을 흉내 낸 시간 그리디와 강의실 그리디입니다.
- 이동 항을 목표에서 빼면 CP-SAT의 먼 이동이 11.2회로 오히려 늘어납니다.
- 합성 데이터 실험이며 실제 편성 결과가 아닙니다.

## 회신 해석 평가

교수 답장을 판정(수용·조건부·거절·확인 필요), 고른 안, 조건(요일·교시·종료 시각)으로 바꾸는 기능의 평가입니다. 키워드 규칙을 비교 기준으로 둡니다.

- **상황:** AI소프트웨어학부 2026-1·2학기 실제 개설 강좌 시간표로 만든 조율 상황 20개. 과목·분반·강의실·시간은 실제 값, 교수 이름은 가명, 겹침과 대안은 꾸민 상황입니다
- **답장:** 팀원 4명이 교수 역할로 직접 쓴 80개. 언어 모델로 만들지 않았습니다
- **정답:** 최재성 한 명이 달았습니다. 16개는 프롬프트를 고칠 때 보는 dev, 64개는 test입니다
- **새 세트:** 규칙·프롬프트를 다 고친 뒤 새 상황 5개(s21~s25)로 받은 답장 20개. 아무도 미리 보지 않은 마지막 평가입니다

결과 (언어 모델 = gemini-3.5-flash-lite)

| 세트 | 방식 | 판정 정확도 | 받아들임 여부 | 고른 안 일치 | 조건 F1 | 처리안 일치 | 위험 오류 |
|---|---|---|---|---|---|---|---|
| test 64 | 키워드 규칙 | 0.500 | 0.656 | 0.625 | 0.331 | 0.578 | 6건 |
| test 64 | 언어 모델, 처음 측정 | 0.812 | 0.984 | 0.953 | 0.840 | 0.938 | 0건 |
| test 64 | 언어 모델, 라벨 규칙 정리 뒤 (낙관적) | 0.906 | 1.000 | 1.000 | 0.860 | 0.969 | 0건 |
| **새 세트 20** | 키워드 규칙 | 0.500 | 0.650 | 0.600 | 0.423 | 0.600 | 3건 |
| **새 세트 20** | **언어 모델** | **0.800** | **1.000** | **1.000** | **0.820** | **0.900** | **0건** |

- 받아들임 여부 = 수용·조건부(고른 안으로 옮김)인지, 거절·확인 필요(시간을 확정하지 않음)인지만 맞혔는가. 이 둘을 헷갈리는 것이 비싼 오류라서 보조 지표로 둡니다 (결과를 본 뒤 11/22에 추가, 모든 방식·세트에 같게 계산). 언어 모델의 판정 오류는 거의 다 수용↔조건부, 거절↔확인 필요처럼 처리 방식만 조금 다른 것끼리였습니다
- 위험 오류 = 정답이 거절·확인 필요인데 수용·조건부로 읽은 수. 키워드 규칙은 "C가 괜찮을 것 같긴 한데… 다음 주에 다시 말씀드려도 될까요"를 C 수용으로 읽는 식의 오류가 있었고, 언어 모델은 두 세트 모두 0건입니다
- **가장 믿을 만한 숫자는 새 세트의 0.80입니다.** test 첫 측정(0.81)과 비슷하고, 규칙 정리 뒤 test 숫자(0.91)는 예상대로 낙관적이었습니다. 다만 20개라 한 문장이 5%p입니다
- 처리 시간은 답장 하나에 평균 4~5초입니다 (키워드 0초)
- 한계: 정답을 한 사람이 달아 일치도(카파)를 잴 수 없습니다. 답장은 팀원이 교수 역할로 쓴 것입니다
- 측정 이력, 바꾼 것, 오류 분석: [docs/planning/회신해석_평가.md](docs/planning/회신해석_평가.md) · 실행: `python eval/run_coord.py reply --method llm --split test`

## 조율 메시지 사람 평가

교수에게 보내는 조율 메시지는 정답이 하나가 아니라 사람이 채점했습니다 (상황 25개, 언어 모델 글 25개 + 틀 문장 25개를 섞어 방식을 가리고 채점, 채점자 1명).

| | 틀 문장 (기준선) | 언어 모델 1차 | 언어 모델 2차 |
|---|---|---|---|
| 내용 맞음 | 1.00 | 0.96 | 0.96 |
| 지어낸 말 없음 | 1.00 | 0.88 | 1.00 |
| 금지 내용 없음 | 1.00 | 1.00 | 1.00 |
| 자연스러움 (1~5) | 5.00 | 3.92 | 4.72 |

- 1차에서 언어 모델이 입력에 없는 이유("다른 과목이 배정되어")를 지어내고, 제목 줄을 문장으로 끝내지 않았습니다. 코드 검사는 이것을 잡지 못했습니다
- 그래서 인사·제목·대안·마지막 문장은 틀로 고정하고, 언어 모델은 상황 설명 문단만 쓰게 바꿨습니다. 설명 문단은 코드가 다시 검사합니다 (대안 설명, 없는 시각, 지어낸 이유, 상대 이름 빠짐)
- 2차에서도 틀 문장이 모든 칸에서 같거나 나았습니다
- 채점 기준·결과: [docs/planning/메시지_사람평가.md](docs/planning/메시지_사람평가.md) · 실행: `python eval/run_coord.py message --method llm`

## 개발 환경 준비

Python 3.11 이상을 기준으로 합니다.

```bash
git clone https://github.com/gnoesj/ssu-room.git
cd ssu-room

python -m venv .venv
# Windows: .venv\Scripts\activate
# macOS·Linux: source .venv/bin/activate
pip install -r backend/requirements.txt

cp .env.example .env   # Windows: copy .env.example .env
```

`.env`에는 각자 발급받은 API 키를 넣습니다. `.env`는 절대 커밋하지 않습니다.

## 저장소 사용 규칙

### 1. 기본 흐름

```
main 최신화 → 브랜치 만들기 → 작업·커밋 → push → PR → 리뷰 1명 승인 → 병합 → 브랜치 삭제
```

```bash
git switch main
git pull
git switch -c feat/solver-hard-rules
# 작업
git add 바꾼파일
git commit -m "solver: 교양필수 시간 규칙 추가"
git push -u origin feat/solver-hard-rules
# GitHub에서 PR 만들기
```

- **main에 직접 push하지 않습니다.** 모든 변경은 PR로 들어갑니다. 무료 비공개 저장소라 설정으로 막을 수 없으니 팀 약속으로 지킵니다.
- 작업을 시작하기 전과 PR을 올리기 전에 `git pull`로 main을 최신으로 맞춥니다.

### 2. 브랜치 이름

`종류/짧은-영어-설명` 형식으로 씁니다.

| 종류 | 언제 | 예 |
|---|---|---|
| `feat/` | 새 기능 | `feat/nlp-reply-classifier` |
| `fix/` | 버그 수정 | `fix/solver-chapel-overlap` |
| `data/` | 데이터·라벨 추가 | `data/reply-labels-v1` |
| `exp/` | 실험 | `exp/greedy-vs-cpsat` |
| `docs/` | 문서·회의록 | `docs/labeling-guide` |

한 브랜치에는 한 가지 일만 담고, 작업이 끝나 병합되면 브랜치를 지웁니다.

### 3. 커밋 메시지

`영역: 무엇을 했는지` 한 줄로 씁니다. 한국어로 씁니다.

```
solver: 교양필수 10:30~15:00 규칙 추가
nlp: 회신 분류 프롬프트 첫 버전
eval: 회신 해석 정확도 계산 스크립트
data: 희망 문장 30개와 정답 추가
docs: 11/4 회의록
```

영역: `rules`, `solver`, `nlp`, `db`, `api`, `frontend`, `eval`, `data`, `exp`, `docs`

### 4. PR과 리뷰

- PR은 작게 만듭니다. 리뷰어가 15분 안에 읽을 수 있는 크기가 좋습니다.
- PR 설명에는 네 가지를 적습니다.
  1. 무엇을 바꿨나
  2. 왜 바꿨나
  3. 어떻게 확인했나 (실행한 명령, 결과)
  4. AI 도구 사용 여부 (도구 이름과 쓴 부분)
- 팀원 1명 이상이 승인해야 병합합니다. 그 영역을 맡은 사람이 리뷰하는 것을 원칙으로 합니다.
- 병합은 PR 작성자가 하고, **Squash and merge**를 씁니다. PR 하나가 커밋 하나로 남아서 누가 무엇을 했는지 보기 쉽습니다.
- 리뷰 의견은 코드 줄에 댓글로 남기고, 고친 뒤 작성자가 답글로 알립니다.

### 5. 올리면 안 되는 것

- `.env`, API 키, 비밀번호
- 실제 수요 조사 양식, 인터뷰 원본, 교수·조교 실명이 들어간 파일
- 영상 등 10MB가 넘는 파일
- 실수로 올렸다면 바로 팀에 알립니다. API 키는 즉시 폐기하고 새로 발급합니다. 기록에서 지우는 것만으로는 안전하지 않습니다.

### 6. 할 일 관리

- 할 일은 GitHub Issues에 올리고 담당자를 지정합니다.
- PR 설명에 `Closes #번호`를 쓰면 병합할 때 이슈가 자동으로 닫힙니다.
- 진행 상황은 Discord에 바로 공유하고, 회의록은 `docs/meetings/날짜.md`로 남깁니다.

### 7. 결정하는 방법

기술 판단은 그 영역 담당자가 정하고 공유합니다. 범위와 일정은 화요일 정기 회의에서 다수결로 정합니다. 체크포인트(11/12, 11/19)에서 범위를 다시 조정합니다.

## 데이터 원칙

- 시연 데이터는 **가상 데이터**이고, 화면과 발표에도 그렇게 표시합니다.
- 평가 문장은 팀원·지인이 교수 역할로 직접 쓰고, **언어 모델로 만들지 않습니다.** 라벨은 최재성 한 명이 달고(11/21 결정), 80개 중 16개는 프롬프트 개선용, 64개는 최종 평가용으로 나눕니다.
- 정답 데이터(`eval/labels/`)는 평가 스크립트만 읽습니다. 서비스 코드는 정답을 읽지 않습니다.
- 가정·시뮬레이션·목표 수치는 실측처럼 쓰지 않습니다.
